

# API_CONTRACT.md
Version: 1.0
Status: LOCKED



## 1. Purpose
This document defines the official API interfaces for the **AI‑POWERED WATER CONTAMINATION TRACKING AND EPIDEMIC EARLY WARNING SYSTEM** prototype.  All implementations – ESP32 firmware, Node.js backend, React frontend, and the Python/Scikit‑learn AI engine – must conform to the contracts described here.  `API_CONTRACT.md` is the source of truth for request/response formats, authentication, error handling, and integration points.

---

## 2. API Design Principles
- **RESTful** endpoints using HTTP verbs.
- **JSON** payloads (`Content‑Type: application/json`).
- All communications over **HTTPS** (TLS 1.2+).
- **Stateless** requests where possible; state is persisted only in MongoDB.
- Consistent error response structure (see Section 12).
- Input validation performed server‑side; malformed requests are rejected with `400 Bad Request`.
- **ISO 8601** timestamps in UTC (e.g., `2026-08-12T12:30:00Z`).
- Stable field names; never change without a version bump (future compatibility).
- No GraphQL, WebSockets, gRPC, or MQTT in the MVP.

---

## 3. Base Configuration
- **Base URL**: `/api`
- **Development example**: `http://localhost:<PORT>/api`
- **Production example**: `https://<domain>/api` (domain is environment‑specific and not fixed here).

---

## 4. Authentication
- Prototype uses a simple **API‑key** mechanism.
- The API key is supplied in the request header `X‑API‑KEY`.
- All API endpoints require a valid X-API-KEY. No public API endpoints are exposed in the MVP.
- Missing or invalid keys result in:
  - HTTP `401 Unauthorized`
  - Error body with code `AUTHENTICATION_ERROR`.
- API keys are stored in backend environment variables (`API_KEY_<SERVICE>`). No JWT or token exchange is used.

---

## 5. Common Conventions
### Content‑Type
`application/json`

### Timestamp
ISO 8601 UTC, e.g., `2026-08-12T12:30:00Z`.

### Location
```json
{"latitude": <float>, "longitude": <float>}
```
- **latitude**: -90 to 90
- **longitude**: -180 to 180

### IDs
- **nodeId**: string identifier assigned to each ESP32 node (e.g., `WATER_001`).
- **readingId**, **symptomId**, **alertId**, **predictionId**: opaque string generated by the backend (e.g., MongoDB ObjectId). No UUID requirement.

## 6. Sensor API
### POST /api/sensor
**Purpose**: Receive water‑quality readings from ESP32 sensor nodes.

**Authentication**: Required (`X‑API‑KEY`).

**Headers**:
- `Content-Type: application/json`
- `X‑API‑KEY: <key>`

**Request Body** (all fields required unless noted):
```json
{
  "nodeId": "WATER_001",
  "timestamp": "2026-08-12T12:30:00Z",
  "latitude": 8.1833,
  "longitude": 77.4119,
  "ph": 6.8,
  "tds": 420,
  "turbidity": 8.4,
  "temperature": 28.2
}
```
- `nodeId`: string, matches registered node.
- `timestamp`: ISO 8601 UTC.
- `latitude` / `longitude`: numeric, within valid ranges.
- `ph`: numeric, typically 0‑14.
- `tds`: numeric (ppm).
- `turbidity`: numeric (NTU).
- `temperature`: numeric, value from DS18B20 waterproof sensor (°C).

**Successful Response** (`201 Created`):
```json
{
  "success": true,
  "message": "Sensor reading accepted",
  "data": {
    "readingId": "<generated-id>",
    "nodeId": "WATER_001",
    "timestamp": "2026-08-12T12:30:00Z"
  }
}
```

**Error Responses**:
- `400 Bad Request` – validation failure (`VALIDATION_ERROR`).
- `401 Unauthorized` – missing/invalid API key.
- `429 Too Many Requests` – rate limit exceeded (see Section 14).
- `500 Internal Server Error` – unexpected backend error.

## 7. Symptom API
### POST /api/symptom
**Purpose**: Receive aggregated community symptom counts for a given location and time window.

**Authentication**: Required.

**Headers**:
- `Content-Type: application/json`
- `X‑API‑KEY: <key>`

**Request Body** (all fields required unless noted):
```json
{
  "location": {
    "latitude": 8.1833,
    "longitude": 77.4119
  },
  "timestamp": "2026-08-12T12:00:00Z",
  "feverCount": 12,
  "diarrheaCount": 5,
  "vomitingCount": 3,
  "abdominalPainCount": 4
}
```
- `location`: object as defined in Section 5.
- `timestamp`: ISO 8601 UTC representing the aggregation period (e.g., start of hour).
- Symptom counts: non‑negative integers.

**Successful Response** (`201 Created`):
```json
{
  "success": true,
  "message": "Symptom report accepted",
  "data": {
    "symptomId": "<generated-id>",
    "timestamp": "2026-08-12T12:00:00Z"
  }
}
```

**Error Responses**: same set as Sensor API (`400`, `401`, `429`, `500`).

## 8. Risk API
### GET /api/risk/:location
**Purpose**: Return the latest risk assessment for the specified location.

**Authentication**: Required.

**Path Parameters**:
- `location` – URL‑encoded string identifying the location (e.g., `lat,lon`). For simplicity the backend expects `lat,lon` format, e.g., `/api/risk/8.1833,77.4119`.

**Headers**:
- `X‑API‑KEY: <key>`

**Successful Response** (`200 OK`):
```json
{
  "success": true,
  "data": {
    "location": {
      "latitude": 8.1833,
      "longitude": 77.4119
    },
    "riskScore": 0.72,
    "riskLevel": "HIGH",
    "timestamp": "2026-08-12T12:45:00Z",
    "contributingFactors": {
      "ph": 6.8,
      "tds": 420,
      "turbidity": 8.4,
      "temperature": 28.2,
      "symptomRate": 0.15,
      "precipitation": 2.3,
      "humidity": 78
    }
  }
}
```
- `riskScore`: floating‑point indicator (0‑1) **not** a medical diagnosis.
- `riskLevel`: one of `LOW`, `MEDIUM`, `HIGH`.
- `contributingFactors` **optional**; included when backend has recent data.

**Error Responses**:
- `404 Not Found` – no risk data for given location.
- `401 Unauthorized` – missing/invalid API key.
- `400 Bad Request` – malformed location parameter.
- `500 Internal Server Error`.

## 9. Weather API
### GET /api/weather/:location
**Purpose**: Provide the cached hourly weather data used by the dashboard and AI engine.

**Authentication**: Required (same API key).

**Path Parameters**: same format as Risk API (`lat,lon`).

**Successful Response** (`200 OK`):
```json
{
  "success": true,
  "data": {
    "location": {
      "latitude": 8.1833,
      "longitude": 77.4119
    },
    "temperature": 27.5,
    "precipitation": 0.0,
    "humidity": 80,
    "source": "OpenWeatherMap",
    "cachedAt": "2026-08-12T12:00:00Z",
    "timestamp": "2026-08-12T12:00:00Z"
  }
}
```
- No external weather API key is exposed; the backend retrieves and caches the data.

**Error Responses**: `401`, `404`, `500` as appropriate.

## 10. AI/ML Interface
The Node.js backend invokes the Python/Scikit‑learn engine as a **scheduled job** (every 15 minutes).

**Input Contract** (passed as JSON to the Python job):
```json
{
  "location": {"latitude": 8.1833, "longitude": 77.4119},
  "timestamp": "2026-08-12T12:45:00Z",
  "water": {
    "ph": 6.8,
    "tds": 420,
    "turbidity": 8.4,
    "temperature": 28.2
  },
  "symptoms": {
    "feverCount": 12,
    "diarrheaCount": 5,
    "vomitingCount": 3,
    "abdominalPainCount": 4
  },
  "weather": {
    "temperature": 27.5,
    "precipitation": 0.0,
    "humidity": 80
  }
}
```
Missing optional fields are represented as null and handled by the ML preprocessing pipeline.

**Output Contract** (stored in `riskScores` collection):
```json
{
  "location": {"latitude": 8.1833, "longitude": 77.4119},
  "timestamp": "2026-08-12T12:45:00Z",
  "riskScore": 0.72,
  "riskLevel": "HIGH",
  "modelVersion": "v1.0"
}
```
- `modelVersion` is optional; included if the backend tracks it.
- The contract does **not** lock a specific algorithm; any scikit‑learn model that produces `riskScore` and `riskLevel` is acceptable.

## 11. Alert Service Interface
When a new risk entry has `riskLevel` of `MEDIUM` or `HIGH`, the backend creates an alert and forwards it to the external SMS/Push provider (e.g., Twilio).  The internal payload sent to the provider is abstracted; the contract below describes the **internal** representation.

**Internal Alert Payload** (JSON, sent via HTTPS to provider SDK):
```json
{
  "alertId": "<generated-id>",
  "location": {"latitude": 8.1833, "longitude": 77.4119},
  "riskLevel": "HIGH",
  "riskScore": 0.72,
  "timestamp": "2026-08-12T12:45:00Z",
  "message": "Water quality risk HIGH at 8.1833,77.4119."
}
```
- The backend formats `message` for the provider; actual phone numbers or credentials are **never** part of the API contract.
- Success/Failure of the external call is logged; failures result in a retry (handled internally, not exposed via API).

## 12. Error Response Contract
All error responses share this structure:
```json
{
  "success": false,
  "error": {
    "code": "<ERROR_CODE>",
    "message": "Human‑readable description",
    "details": []
  }
}
```
**Standard error codes**:
- `VALIDATION_ERROR`
- `AUTHENTICATION_ERROR`
- `RATE_LIMIT_EXCEEDED`
- `NOT_FOUND`
- `METHOD_NOT_ALLOWED`
- `INTERNAL_ERROR`

Corresponding HTTP status codes:
- `400 Bad Request`
- `401 Unauthorized`
- `403 Forbidden` (if API key lacks permission – not used currently)
- `404 Not Found`
- `405 Method Not Allowed`
- `429 Too Many Requests`
- `500 Internal Server Error`
- `503 Service Unavailable`

## 13. Validation Rules
| Field | Type | Constraints |
|-------|------|-------------|
| `ph` | number | 0 ≤ value ≤ 14 |
| `tds` | number | ≥ 0 |
| `turbidity` | number | ≥ 0 |
| `temperature` | number | plausible water range –50 ≤ °C ≤ 100 |
| `latitude` | number | -90 ≤ value ≤ 90 |
| `longitude` | number | -180 ≤ value ≤ 180 |
| `timestamp` | string (ISO 8601) | must be valid UTC datetime |
| `nodeId` | string | non‑empty, matches registered pattern |
| Symptom counts (`feverCount`, …) | integer | ≥ 0 |
| `riskScore` | number | 0 ≤ value ≤ 1 |
| `riskLevel` | string | one of `LOW`, `MEDIUM`, `HIGH` |

---

## 14. Rate Limiting
- **POST /api/sensor**: max **60 requests per minute per `nodeId`**.
- Exceeding the limit returns `429 Too Many Requests` with error code `RATE_LIMIT_EXCEEDED`.
- Other endpoints follow standard server defaults (no strict limit for this MVP).

---

## 15. Idempotency / Duplicate Handling
- Duplicate sensor submissions are identified by the composite key **`nodeId` + `timestamp`**.
- If a reading with the same key already exists, the backend returns `200 OK` with a message indicating the duplicate and includes the existing `readingId`.
- No additional idempotency tokens are required.

---

## 16. API ↔ Database Mapping
| API Endpoint | MongoDB Collection |
|--------------|--------------------|
| `POST /api/sensor` | `waterReadings` |
| `POST /api/symptom` | `symptoms` |
| `GET /api/weather/:location` (internal cache) | `weather` |
| Scheduled ML inference (internal) | reads `waterReadings`, `symptoms`, `weather`; writes `riskScores` |
| `GET /api/risk/:location` | reads `riskScores` |

## 17. Frontend Integration
- **GIS map** → `GET /api/risk/:location` (display risk markers).
- **Weather panel** → `GET /api/weather/:location` (show current weather).
- **Symptom form** → `POST /api/symptom` (submit community reports).
- **Dashboard status** may optionally request recent sensor readings via a future endpoint (not required for MVP).

---

## 18. Hardware Integration
- ESP32 connects to Wi‑Fi, constructs a JSON payload as defined in Section 6, and sends an **HTTPS POST** to `POST /api/sensor`.
- On network failure, the node buffers up to 24 h of readings locally and retries until acknowledgement (HTTP `201` with `success:true`).
- The ESP32 **never** talks directly to MongoDB, the AI engine, or external services.

---

## 19. API Versioning
- Current MVP uses a **single version** (`/api`).
- Future releases may introduce version prefixes (`/api/v1`) while preserving backward compatibility; clients must continue to support the un‑versioned paths until deprecated.

---

## 20. Security Rules
- All endpoints served over **HTTPS**; TLS 1.2+ enforced.
- **API keys** are stored in environment variables and never committed to source.
- Input validation prevents injection attacks.
- Rate limiting mitigates abuse.
- No secret (weather API key, Twilio credentials) is ever returned to clients.
- ESP32 cannot access MongoDB or AI engine directly; all interactions go through the REST API.

---

## 21. Example End‑to‑End Flow
1. **ESP32** collects sensor data and sends `POST /api/sensor`.
2. Backend validates, stores the reading in **MongoDB** (`waterReadings`).
3. Every 15 minutes a scheduled job runs the **Python/Scikit‑learn** engine using the latest data.
4. Engine writes a new document to **riskScores**.
5. Frontend GIS dashboard calls `GET /api/risk/:location` to display the latest risk.
6. If the returned `riskLevel` is `MEDIUM` or `HIGH`, backend creates an alert payload and forwards it to the SMS/Push provider.
7. Users receive an SMS or push notification.

## Consistency Check
- All endpoints (`/api/sensor`, `/api/symptom`, `/api/risk/:location`, `/api/weather/:location`) match those defined in **PROJECT_ARCHITECTURE.md**.
- Communication flow is **ESP32 → Wi‑Fi → HTTPS POST → Node.js REST API**; no MQTT or LoRa used in the MVP.
- Temperature field is explicitly named `temperature` and sourced from the **DS18B20** sensor.
- Risk output contains `riskScore` and `riskLevel` (values `LOW`, `MEDIUM`, `HIGH`).
- AI model algorithm is not locked; only the input/output contract is defined.
- Weather API key and SMS provider credentials remain internal.
- No component accesses MongoDB directly except the backend.
- No medical diagnosis or accuracy claims are made.
